## 📖 Project Description

The **Enterprise SIEM Lab** is a fully operational, end-to-end Security Information and Event Management (SIEM) laboratory built on the [Wazuh](https://wazuh.com/) open-source platform integrated with the **Elastic Stack** (Elasticsearch + Kibana). The project covers the complete SIEM deployment lifecycle:

| Phase | Activity |
|-------|----------|
| **Infrastructure** | Multi-container Wazuh cluster deployed via Docker Compose |
| **Collection** | Wazuh agents on Linux (Ubuntu, CentOS) and Windows 10 endpoints |
| **Detection** | Custom XML detection rules mapped to MITRE ATT&CK techniques |
| **Simulation** | Python `LogSimulator` class generating realistic attack events |
| **Enrichment** | Wazuh REST API client for alert retrieval and MITRE enrichment |
| **Visualisation** | Four custom Kibana dashboard panels + Matplotlib analytics |

### Why Wazuh?

| Feature | Wazuh (Open-Source) | Splunk / QRadar (Commercial) |
|---------|---------------------|------------------------------|
| License Cost | **Free** | $50k–$500k+/year |
| Detection Rules | **7,000+ built-in** | 3,000–5,000 |
| MITRE ATT&CK Mapping | **Native** | Add-on required |
| Docker Deployment | **Official image** | Complex |
| REST API | **Full OpenAPI spec** | Proprietary |

## 📊 Dataset & Data Sources

This project uses **synthetic log data** generated by the `LogSimulator` class (no real attack traffic). In a live deployment, logs are collected from real endpoints.

### Simulated Log Sources

| Source | Log Format | Location | Events Simulated |
|--------|-----------|----------|-----------------|
| SSH daemon (`sshd`) | syslog | `/var/log/auth.log` | Brute-force failed logins |
| `sudo` audit | syslog | `/var/log/auth.log` | Privilege escalation attempts |
| Wazuh FIM / syscheck | ossec | Internal | `/etc/passwd`, `/etc/sudoers` modifications |
| Linux kernel (UFW) | syslog | `/var/log/kern.log` | Port scan (SYN flood) |
| rkhunter / rootcheck | ossec | Internal | Rootkit / hidden file detection |
| Custom simulation | syslog | `/var/log/siem_sim.log` | All above scenarios (controlled) |

### Real-World Dataset References

| Dataset | URL | Used For |
|---------|-----|----------|
| Wazuh Sample Alerts | https://documentation.wazuh.com/current/proof-of-concept-guide/ | Rule baseline validation |
| CICIDS 2017/2018 | https://www.unb.ca/cic/datasets/ids-2017.html | Reference network intrusion patterns |
| MITRE ATT&CK STIX | https://github.com/mitre/cti | Technique ID mapping |
| Elastic Security Labs | https://www.elastic.co/security-labs | Elasticsearch alert schema reference |

> **Note:** The simulation log file `siem_sim.log` is generated at runtime by running Cell 8.2 of the notebook. It is not committed to the repository.

### Step 4 — Deploy the Wazuh Cluster (Optional — for live SIEM)

> Skip this step if you only want to run the notebook in demo/simulation mode.

```bash
# Clone the official Wazuh Docker repository
git clone https://github.com/wazuh/wazuh-docker.git --branch v4.7.2
cd wazuh-docker/single-node

# Generate TLS certificates
docker-compose -f generate-indexer-certs.yml run --rm generator

# Required kernel parameter for Elasticsearch
sudo sysctl -w vm.max_map_count=262144
echo 'vm.max_map_count=262144' | sudo tee -a /etc/sysctl.conf

# Start the full Wazuh stack
docker-compose up -d

# Verify all containers are healthy
docker-compose ps
```

Access the dashboard at: **https://192.168.100.10**
Default credentials: `admin` / `SecurePass123!`

---

### Step 5 — Deploy Agents (Optional — for live SIEM)

Run the provisioning script on each Linux endpoint:

```bash
sudo bash deploy_agent.sh
```

For Windows, download the MSI installer from the Wazuh dashboard and use the enrollment key.

## ✨ Key Features

### 1. Multi-Node Wazuh SIEM Cluster
- Fully containerised deployment using Docker Compose
- Three-service architecture: Manager, Indexer (Elasticsearch), Dashboard (Kibana)
- TLS 1.3 encrypted communication on all inter-service channels
- Persistent Docker volumes for configuration, logs, and index data

### 2. Multi-Source Log Aggregation
- Ingests syslog, Windows Event Log, auth logs, kernel logs, and FIM events
- Agentless syslog receiver on UDP/514 for network devices
- Custom simulation log channel `/var/log/siem_sim.log` for controlled testing

### 3. Custom Detection Rules (XML)
- 6 custom rules (IDs 100010–100031) extending Wazuh's 7,000+ default ruleset
- Frequency-based correlation (brute-force: 8 events in 60 seconds)
- All rules tagged with MITRE ATT&CK technique IDs

### 4. Python Log Simulator
- `LogSimulator` class with 4 simulation methods
- Generates syntactically valid syslog-format events
- Configurable attack IP pools, target users, burst intervals
- Writes to a monitored log file — triggers real Wazuh detections in live mode

### 5. Wazuh REST API Client
- `WazuhAPIClient` class with JWT token authentication
- Methods: `get_agents()`, `get_alerts()`, `test_rule()`
- MITRE ATT&CK enrichment applied to all retrieved alerts

### 6. Elasticsearch DSL Query Library
- 4 production-ready aggregation queries saved to `es_queries.json`
- Covers: top attacking IPs, alert timeline, MITRE frequency, agent health

### 7. Custom Alert Dashboard (4 Panels)
- **Panel 1** — Alert timeline by severity (line chart, 24h window)
- **Panel 2** — Top 10 attacking source IPs (horizontal bar chart)
- **Panel 3** — MITRE ATT&CK technique frequency (bar chart)
- **Panel 4** — Agent health monitor (status table with colour-coded severity)

## 🎯 Detection Rules & MITRE ATT&CK Mapping

| Rule ID | Level | Description | MITRE Technique | Tactic |
|---------|-------|-------------|----------------|--------|
| `100010` | 12 — High | SSH Brute Force: 8+ failures from same IP in 60s | [T1110.001](https://attack.mitre.org/techniques/T1110/001/) | Credential Access |
| `100011` | 14 — Critical | SSH Brute Force from unexpected geography | [T1110.001](https://attack.mitre.org/techniques/T1110/001/) | Credential Access |
| `100020` | 14 — Critical | sudo command not allowed for user | [T1548.003](https://attack.mitre.org/techniques/T1548/003/) | Privilege Escalation |
| `100021` | 13 — Critical | Non-root user opened root session via su | [T1548.003](https://attack.mitre.org/techniques/T1548/003/) | Privilege Escalation |
| `100030` | 10 — High | FIM: Critical authentication file modified (`/etc/passwd`, `/etc/shadow`, `/etc/sudoers`) | [T1078.003](https://attack.mitre.org/techniques/T1078/003/) | Persistence |
| `100031` | 8 — Medium | FIM: New file added to `/etc` directory | [T1078.003](https://attack.mitre.org/techniques/T1078/003/) | Persistence |

### Alert Severity Scale

| Wazuh Level | Tier | Color | Example |
|-------------|------|-------|---------|
| 0 – 3 | Informational | 🔵 | Successful login, config read |
| 4 – 6 | Low | 🟢 | Single failed login |
| 7 – 9 | Medium | 🟡 | Port scan, multiple auth failures |
| 10 – 12 | High | 🟠 | Brute force detected, FIM critical file |
| 13 – 15 | Critical | 🔴 | Root access, rootkit, sudo abuse |

## 📈 Custom Alert Dashboard

The custom Kibana dashboard was designed for Tier 1 SOC analyst triage and provides four real-time panels:

```
┌─────────────────────────────────┬──────────────────────────────────┐
│  Panel 1 — Alert Timeline       │  Panel 2 — Top Attacking IPs     │
│  (Line chart — 24h severity)    │  (Horizontal bar — top 10 IPs)   │
├─────────────────────────────────┼──────────────────────────────────┤
│  Panel 3 — MITRE ATT&CK Map     │  Panel 4 — Agent Health Monitor  │
│  (Bar chart — technique freq.)  │  (Status table — heartbeat/alerts)│
```

All panels query the `wazuh-alerts-4.x-*` Elasticsearch index using the DSL queries defined in [`es_queries.json`](es_queries.json).
